1. PokéStock, c’est quoi ?

PokéStock est ton application personnelle de gestion d’achat-revente de cartes Pokémon.

Elle ne sert pas seulement à tenir un inventaire : elle couvre pratiquement tout le cycle de vie d’une carte :

achat / estimation → entrée en stock → gestion du lot → vente / échange → analyse → historique

et elle contient aussi des workflows spécialisés pour :

les brocantes ;
les Drops Vinted ;
les estimations de collections/annonces ;
les échanges ;
les rachats de cartes ;
la collection personnelle ;
le suivi des cotes ;
les statistiques et compteurs.

L’application est développée en Python + Streamlit et existe à la fois :

en local ;
sur Streamlit Cloud ;
avec le code versionné sur GitHub klanox/appli-des-lots-pokemon, branche main.

Le projet local principal est :

C:\Users\User\Desktop\Appli des lots pokemon

4. 💰 Vente / Échange

C’est un des modules centraux de PokéStock.

Il comporte deux espaces :

Vente

Le but est de rechercher les cartes réellement disponibles dans ton stock, de les mettre dans un panier puis d’enregistrer une transaction.

Recherche

Le moteur permet de rechercher notamment par :

nom ;
numéro ;
extension ;
variantes et métadonnées disponibles.

La recherche est live : les résultats évoluent pendant que tu tapes.

Hors recherche, les cartes conservent une présentation organisée selon leurs lots.

Lorsqu’une recherche est active :

les séparations par lot disparaissent ;
les cartes deviennent une grille continue ;
les exemplaires les plus anciennement acquis sont prioritaires.

Cela permet notamment d’écouler en premier les cartes les plus anciennes.

Cartes

Une carte affichée peut contenir :

image ;
nom ;
numéro ;
extension ;
lot d’origine ;
quantité disponible ;
prix de vente ;
coût d’acquisition ;
statut ;
bouton d’ajout au panier.

Les images passent désormais par une résolution centralisée pouvant prendre en compte :

image API ;
image personnalisée ;
anciens champs d’image ;
cache ;
fallback TCGDex.
Quantités

Si une carte existe en plusieurs exemplaires, la quantité peut être choisie avant l’ajout au panier.

Les cartes possèdent des identifiants stables, notamment card_uid, ce qui évite les confusions lorsque plusieurs cartes semblables sont présentes dans un lot.

5. 🛒 Panier de vente

Le panier est aujourd’hui capable de contenir plusieurs types de produits dans une même transaction.

Il peut mélanger :

cartes physiques en stock ;
articles hors stock.

Chaque ligne garde :

quantité ;
prix ;
origine ;
nature de l’article ;
coût d’acquisition lorsqu’il est connu.
Prix négocié

Le prix final de la commande peut être différent de la somme initiale.

PokéStock recalcule alors la vente selon le montant réellement encaissé.

Bénéfice estimé

Le panier peut afficher :

prix total ;
coût d’achat estimé ;
bénéfice de la commande.

Si une partie du coût est inconnue, le bénéfice est signalé comme partiel plutôt que d’inventer un coût.

6. Vente hors stock

Une vente hors stock correspond à quelque chose vendu mais qui n’existe pas comme carte physique inventoriée.

Par exemple :

bulk ;
classeur ;
tin ;
produit divers ;
article accessoire.

Elle peut être ajoutée au même panier que des cartes physiques.

Avant validation finale :

aucune vente n’est créée ;
aucun chiffre d’affaires n’est comptabilisé.

C’est seulement lorsque le panier complet est validé que la transaction existe réellement.

7. Transactions de vente

Une commande complète reçoit un :

sale_transaction_id

commun à toutes ses lignes.

Cela signifie qu’une vente contenant :

3 cartes ;
1 classeur hors stock ;

reste une seule transaction commerciale.

Les statistiques peuvent ainsi distinguer :

nombre de cartes vendues ;
nombre de transactions ;
panier moyen.
Annulation

Si une transaction est annulée :

toutes les lignes de la transaction sont annulées ensemble ;
le stock physique est restauré ;
les articles hors stock ne créent évidemment pas de stock ;
le CA est retiré ;
les statistiques sont recalculées proprement.

Les anciennes ventes créées avant l’existence de sale_transaction_id restent compatibles.

8. 🔄 Échange

Le deuxième volet de Vente / Échange est un véritable moteur économique d’échanges.

Un échange peut contenir :

Ce que tu donnes
une ou plusieurs cartes ;
différentes quantités ;
éventuellement de l’argent.
Ce que tu reçois
une ou plusieurs cartes ;
éventuellement de l’argent.

Le contrôle cash permet :

Aucun / Tu reçois / Tu ajoutes

9. Règle fondamentale : un échange n’est pas une vente

PokéStock fait une différence stricte.

Une carte donnée dans un échange :

❌ ne crée pas de vente
❌ ne crée pas de CA
❌ ne reçoit pas un faux prix de vente

Elle sort du stock via des mécanismes dédiés du type :

exchange_out_quantity
exchange_out_entries

Cela évite de fausser toutes les statistiques.

10. Coût économique des échanges

PokéStock conserve la vraie valeur historique des cartes que tu donnes.

La logique actuelle est essentiellement :

coût économique restant = coût historique des cartes données + argent ajouté - argent reçu

avec un minimum de 0.

Exemple :

cartes données : coût historique 80 €
tu ajoutes 20 €

→ coût transmis aux cartes reçues : 100 €

Si tu reçois 15 € avec les cartes :

→ coût transmis : 85 €

L’argent reçu dans un échange :

❌ n’est pas du CA.

15. Remboursement d’un lot

Chaque lot possède maintenant une jauge financière intégrée directement dans sa carte.

Exemple :

Lot acheté : 255,49 €
CA généré : 322,50 €

PokéStock affiche :

✓ Remboursé · 126,2 %

La formule est toujours financière :

CA généré par le lot / coût historique du lot

Elle ne se transforme plus en progression du nombre de cartes après remboursement.

Le pourcentage peut donc monter à :

110 %
150 %
220 %
etc.

La barre visuelle est plafonnée à 100 %, mais le vrai pourcentage reste affiché.

Couleurs
rouge : moins de 70 %
orange : 70 à moins de 100 %
vert : 100 % ou plus

La jauge et le header sont désormais dans une seule surface blanche, depuis le correctif 3d7ccdf.

16. % de la cote à l’achat

À côté du prix d’un lot, PokéStock peut afficher le pourcentage auquel tu as acheté le lot par rapport à sa valeur estimée.

Exemple :

255,49 € · 73,5 % cote

Cela signifie :

prix payé / valeur estimée du lot

La valeur de référence peut venir des informations du lot ou être reconstruite à partir des cartes.

17. Lots de rachat Brocante

Un nouveau type de lot est progressivement utilisé pour les rachats réalisés en Brocante.

Pour une même brocante :

le premier rachat crée le lot journalier ;
tous les rachats suivants rejoignent ce même lot.

Contrairement à un lot classique, les cartes peuvent arriver sans coût individuel immédiatement réparti.

Le coût global du rachat est connu, mais la répartition attend les prix de vente.

18. Répartition différée du coût

Exemple :

Tu rachètes :

Dracaufeu ;
Pikachu ;

pour 10 € au total.

Au moment du rachat :

coût du lot = 10 € ;
aucun coût fictif de 5 €/5 € n’est inventé.

Plus tard dans Lots, tu renseignes :

Dracaufeu : prix de vente 15 €
Pikachu : prix de vente 5 €

Total = 20 €.

PokéStock répartit alors :

Dracaufeu : 75 % → coût historique 7,50 €
Pikachu : 25 % → coût historique 2,50 €

Total = exactement 10 €.

Une fois cette répartition figée, modifier ensuite le prix de vente ne doit pas réécrire arbitrairement l’histoire économique.

Avant répartition, les cartes concernées sont protégées contre vente/échange afin d’éviter un faux bénéfice.

34. Suppression Brocante

Il existe aussi une suppression transactionnelle.

Elle n’est pas une simple suppression de ligne.

PokéStock tente de restaurer proprement :

ventes ;
stock ;
rachats inutilisés ;
frais ;
hors stock.

Mais si une donnée a ensuite été réutilisée, la suppression est bloquée.

Exemples :

carte rachetée puis revendue ;
carte utilisée dans un échange ;
dépendance historique ambiguë.

Cela évite de casser l’historique économique.

35. 🛍️ Drop Vinted

C’est probablement le workflow spécialisé le plus complexe de l’application.

Il sert à préparer de gros Drops Vinted de cartes Pokémon.

Le processus est divisé en 5 étapes.

L’étape 4 (Création des annonces) est affichée en « une page » aérée sur ordinateur, avec le MÊME cadre que les 4 autres étapes (bandeau PokéStock, bloc « Drop Vinted », 5 pastilles, « Drop à afficher » + « Nouveau Drop », carte du Drop), compacté de façon identique sur les 5 étapes ; aucun défilement de la page, tout reste accessible, le secondaire est dans le menu « ⋯ Plus » et l’icône ⓘ du cockpit (voir sections 35 et 43).
Cadre commun des 5 étapes (15/10/2026, ui/pages/vinted_listings.py : _DROPFRAME_CSS, _inject_vinted_dropframe_styles, marqueur .ps-dropframe-marker) : les étapes 1 à 5 affichent exactement les mêmes composants dans le même ordre — bandeau « PokéStock — Collection, lots et ventes sous contrôle », bloc « Drop Vinted — Préparer, suivre et analyser tes drops Vinted », rangée des 5 pastilles larges, « Drop à afficher » (libellé à gauche du sélecteur) + « Nouveau Drop », carte du Drop (nom, nombre de cartes, valeur, canal, « ⚙ Gérer »). Ce cadre est compacté de la même façon sur les 5 étapes (écran large uniquement ; le mobile est inchangé) : décalage du haut de page 62 px (sous la barre Streamlit), bandeau 40 px, bloc Drop Vinted 46 px, pastilles 34 px, sélecteur et « Nouveau Drop » 36 px, carte du Drop sur une ligne, 8 px entre ces éléments ; les éléments invisibles (styles, scripts) ne comptent plus dans l’espacement. Couleurs, pastilles, boutons et dégradés sont ceux de l’application ; seuls les tailles et espacements changent. L’ancienne ligne compacte propre à l’étape 4 (ps_topbar, ps-topbar-marker, STEP4_TOPBAR_FLAG) et la compaction propre à l’étape 5 ont été supprimées. Le contenu propre à chaque étape garde ses espacements habituels.

Les titres et descriptions d’annonces sont calculés à l’affichage (aucune écriture de données) et enrichis de mots courts que les acheteurs recherchent (Shiny, AR, Gold, Alt, FA) placés avant le numéro de la carte, d’après une table de règles du code et la rareté récupérée depuis TCGdex (voir section 43 et Santé des données).

39. Reconnaissance automatique des photos

Le moteur de reconnaissance n’utilise pas GPT, Gemini ou autre modèle génératif.

Il repose sur :

RapidOCR ;
ONNX Runtime ;
matching visuel/artwork ;
règles métier ;
numéro ;
langue ;
set ;
variante ;
verso ;
LEGEND ;
V-UNION ;
groupes multi-cartes.

Il possède également un cache persistant permettant de ne pas tout recalculer.

Progression de l’analyse (octobre 2026) :

« Mettre à jour l’analyse », « Relancer l’analyse » et « Actualiser les cartes du Drop » affichent une barre de progression avec la phase (lecture des photos, regroupement des annonces, reconnaissance des cartes), « Photo X / N », le temps écoulé et le temps restant estimé ;
l’estimation est une moyenne glissante du temps des dernières photos (8) x photos restantes, et reste « estimation en cours… » pendant les 3 premières photos de chaque phase ;
à la fin : « Analyse terminée en X min Y s » (conservé après le rechargement de l’écran) ;
si le résultat vient du cache et revient en moins de 0,4 s, rien ne s’affiche ;
techniquement : services/analysis_progress.py (suivi sans Streamlit) + un simple paramètre progress_callback(phase, done, total) dans analyze_sample / refresh_result_candidates / _recognize_groups ; le callback ne reçoit que des compteurs, ne modifie jamais le résultat et une erreur d’affichage ne peut pas casser l’analyse.

« Actualiser les cartes du Drop » (octobre 2026, correctif barre de chargement) :
le bouton est dans « Options de l’analyse » (étape 4 / photos). Il relit le stock et les cartes du Drop (active_drop_candidates), recalcule seulement les annonces touchées, enregistre l’analyse puis met à jour les statuts du Drop ; sur le vrai Drop (420 cartes, 133 de réassort) la dernière analyse mesurée a pris 29 s pour 41 annonces ;
avant : la barre n’était dessinée qu’à l’endroit de l’appel, donc sous l’expander (hors de l’écran), et le chemin « rien n’a changé » n’émettait aucun événement : aucun indicateur, aucun message ;
maintenant : un emplacement (st.empty) est créé tout en HAUT de l’étape et reçoit la barre ; le texte de départ « Lecture du stock et des cartes du Drop… » s’affiche tout de suite, puis une phase par étape : « Lecture du stock et des cartes du Drop » (0–10 %), « Recalcul de l’analyse · Photo X / N · reste environ … · écoulé … » (10–85 %), « Enregistrement de l’analyse » (85–93 %), « Mise à jour des statuts du Drop » (93–100 %) ;
message de fin toujours affiché, même si l’opération dure moins d’1 s : « Actualisation terminée en 12 s : 420 carte(s) du Drop prises en compte, 0 changement (…) » ou « …, 7 carte(s) modifiée(s), 3 annonce(s) recalculée(s) » ; il survit au rechargement de l’écran ;
le chargement automatique de l’écran (reprise de l’analyse enregistrée) utilise la même barre (« Mise à jour automatique des cartes du Drop ») mais sans message de fin ;
techniquement : AnalysisProgress accepte phase_ranges / phase_labels, nouvelles phases candidats / enregistrement / statuts (étapes simples) ; _run_with_analysis_progress(slot=, always_show=, start_text=, phase_ranges=, phase_labels=, done_message=) ; _refresh_candidates_with_progress ; aucun résultat d’analyse n’est modifié (compteurs seulement) ;
inventaire des boutons longs : Actualiser les cartes du Drop, Mettre à jour l’analyse, Relancer l’analyse, première analyse des photos (barre en haut de l’étape) ; étape 3 « actualiser les annonces non validées » et déplacement d’une photo (barre + spinner existants) ; Santé des données : Scanner (spinner existant) et boutons « 🛠️ » de correction (spinner ajouté : sauvegarde, correction, nouveau scan) ; Récupérer la rareté des cartes (barre par lots et bouton Annuler, existants) ; Santé des données « extensions » : les boutons d’écriture (certaines, probables, choix manuel) affichent maintenant un spinner d’écriture ; l’import de photos n’a pas de téléversement (dossier choisi par chemin), seule l’analyse est longue.

41. Étape 3 — Vérification

Le moteur classe les résultats visuellement :

✓ Reconnu
! À vérifier
× Non reconnu

Une carte peut être :

validée ;
marquée mauvaise ;
associée manuellement ;
passée provisoirement.

Pour les annonces multi-cartes :

chaque sous-carte physique possède sa propre validation.

Une carte associée manuellement (même absente des propositions du moteur) conserve l’identifiant de la carte du Drop (drop_item_id) dans le payload. Elle passe donc de « à photographier » à photographiée, l’annonce multi-cartes peut passer à « créée », et la phrase « N cartes de réassort n’ont pas encore de photo reconnue » ne la compte plus.

Prix des cartes à l’étape Vérification (15/10/2026, affichage uniquement, ui/pages/vinted_listings.py : _candidate_stock_price, _price_chip_html, _render_group_price_total) : le bloc « Carte proposée » (ou « Carte N » pour une annonce multi-cartes) affiche sous le nom/numéro un badge avec le prix de vente de la carte, par exemple « 10,00 € ». C’est le même prix que celui de l’annonce à l’étape 4 : suggested_price() de la carte du stock (même uid), avec repli sur le prix du candidat du Drop, comme _recognition_listing_cards. Prix vide ou 0 : badge rouge « Prix manquant ». Annonce multi-cartes : un prix par carte puis une ligne « Total annonce : X € » (somme des cartes retenues), avec « N prix manquant(s) » si besoin. Dans « Corriger l’identification », chaque option de la liste « Carte exacte » (et donc chaque résultat de « Rechercher par nom, numéro ou UID ») est de la forme « Nom · numéro · extension · 10,00 € · Dans le Drop · card_… » : le prix est placé AVANT l’identifiant technique pour rester lisible quand la ligne est tronquée ; carte hors Drop = « hors Drop » avec son prix de stock ; « Pas en stock » à la place du prix pour une carte ni en stock ni dans le Drop (cas rare : la recherche ne propose que des cartes du Drop ou du stock). Plusieurs exemplaires (uid différents) d’une même carte dans le Drop sont listés séparément avec leur propre prix. Aucune écriture : ni statut, ni validation, ni prix, ni logique de reconnaissance ne changent. Non modifiés (à signaler) : le détail « Détails de reconnaissance » (top 3 des candidats, sans prix), la ligne « Annonce #N » et l’étape 2 « Tri des photos », qui ne propose aucune carte ; le rattachement manuel (« Associer une carte ») et la correction passent par le même écran, donc affichent le prix. Tests : tests/test_review_prices.py.

Bouton « 🔄 Actualiser l’analyse » (octobre 2026), en haut de l’écran de vérification :

il relance la reconnaissance des seules annonces NON validées, après que tu as validé ou corrigé des cartes ;
jamais modifiés : annonces validées (« Correct », « Correspondance validée »), associations manuelles, regroupements confirmés, corrections d’identification, ainsi que les annonces déjà traitées dont toutes les cartes sont en ligne ou vendues ;
les cartes déjà attribuées à une annonce validée ou publiée sont retirées des propositions des autres annonces (sauf si le Drop en contient plusieurs exemplaires) ; l’OCR déjà lu est réutilisé ;
la barre de progression ne compte que les photos concernées ; à la fin : « N annonces revérifiées · X propositions changées · Y passées en « Reconnu » · Z restent à vérifier » ;
ta position dans la file est conservée (même annonce, ou la suivante si elle est devenue « Reconnu ») ;
ce n’est PAS le même bouton que « Mettre à jour l’analyse » (étape 2) : celui-ci rematche les annonces touchées par un changement des cartes du Drop ; « Actualiser l’analyse » tient compte de ce que tu as validé. Le regroupement des photos n’est jamais recalculé ;
aucun statut de carte (en ligne, vendu, brouillon) n’est changé et vinted_drops.json n’est pas écrit ;
techniquement : reverify_unvalidated_groups (photo_recognition_service.py), paramètre blocked_counts de _recognize_groups, _rebase_review_pass_after_refresh (vinted_listings.py).

Corrections de la vérification (octobre 2026, étape 2 du Drop) :

Messages précis : « Carte peut-être absente du Drop » est remplacé, à l’affichage, par « Déjà publiée dans le Drop : <nom> <numéro> · <extension> (en ligne / vendue) » quand l’OCR correspond fortement (nom + numéro) à une carte déjà publiée, « Absente des cartes à traiter » si la carte est dans le Drop mais hors périmètre pour une autre raison, et « Absente du Drop » seulement si elle n’est nulle part. Le calcul porte sur toutes les références du Drop ; les candidats de reconnaissance ne changent pas.
Groupe « Déjà publiée — ignorée » : un groupe signalé « absent du Drop » dont l’OCR correspond fortement à une carte en ligne / vendue sort de « À vérifier », ne bloque plus « Continuer » et ne génère aucune annonce. Jamais de masquage silencieux : compteur « N groupes ignorés (déjà publiés) » avec liste dépliable et bouton « Ce n’est pas la bonne carte » (le groupe revient dans « À vérifier » et n’est plus ignoré automatiquement, par exemple pour un 2e exemplaire). Le toggle « Consulter aussi les reconnaissances automatiques » marque « Déjà publiée — ignorée » et « Annonce déjà créée ».
Garde-fou numéro : un numéro complet lu par l’OCR, incompatible avec la carte proposée alors que seul le nom la soutient (ni numéro, ni preuve visuelle), empêche le statut « Reconnu » : l’annonce passe en « À vérifier » avec « Plus probable : <carte> (<statut>) » quand le Drop contient une carte correspondant à la lecture. Une validation manuelle reste prioritaire.
Verso orphelin : un verso qui ouvre un groupe est rattaché à l’annonce précédente si celle-ci n’a qu’un recto (le reste se regroupe normalement, sans renuméroter les annonces). Un recto ou un verso sans pendant reste signalé.
Actions sous chaque photo (annonce à une carte) : « Rattacher à l’annonce précédente », « Rattacher à l’annonce suivante », « Photo de détail » (photo de défaut conservée dans l’annonce mais qui ne sert pas à identifier la carte). Le choix est mémorisé par identité de photo dans la session de vérification et rejoué après une nouvelle analyse. Les validations des deux groupes concernés sont invalidées (l’écran indique lesquelles) et seuls ces deux groupes sont rematchés avec l’OCR en cache ; les autres annonces ne changent jamais. « Grouping incorrect » enregistre désormais le signalement au lieu de seulement passer au cas suivant.
« Cette carte n’est pas dans mon stock » : le groupe sort de « À vérifier », ne bloque plus « Continuer » ni les autres annonces et ne crée aucune annonce. Il est mémorisé (photos + nom / numéro / extension lus si l’OCR est lisible) dans la session de vérification uniquement ; un bandeau « N cartes à enregistrer dans le stock » les liste avec leurs photos, et « Remettre dans la vérification » annule. Aucune carte n’est créée dans data.json ni dans le Drop : après ajout au stock puis au Drop et « Actualiser l’analyse », le groupe repasse normalement.
Techniquement : services/photo_review_actions.py (nouveau), clés de session review_dispositions / published_rejected / photo_moves / grouping_flagged / regroup_log (ancienne session chargée sans erreur), garde-fou ocr_conflict_blocks_recognition (photo_recognition_service.py) ; le moteur de reconnaissance n’est pas modifié. Limite connue : les numéros à un chiffre (ex. M24F) restent un point du moteur laissé de côté.

Le grouping doit également être confirmé lorsqu’il est réellement ambigu.

42. Système de passes de vérification

La vérification fonctionne par passe.

Une passe mémorise :

les groupes présents au départ ;
la position ;
les éléments déjà parcourus.

À la fin :

Vérification terminée

puis tu peux explicitement relancer :

Revoir les X cas non résolus

Cela évite de revenir automatiquement au premier problème en boucle.

« 🔄 Actualiser l’analyse » conserve la passe en cours : la position reste sur la même annonce (ou la suivante si elle est devenue « Reconnu »), sans retour à l’annonce n° 1.

Après un rattachement de photo ou une action « Déjà publiée / pas dans mon stock », la passe est recalée sur le groupe concerné (ou le suivant) et les groupes ignorés ne comptent plus parmi les cas à traiter.

Le moteur prepare_listing() génère le contenu des annonces. Mots recherchés dans le titre et la description (mis à jour le 15/10/2026, abréviations courtes) : services/vinted_listing_service.py ajoute à une annonce à une carte les mots manquants, sans jamais écrire dans les JSON (recalcul à l’affichage). Une carte n’a jamais deux abréviations de rareté : priorité Alt, Gold, AR, FA, puis « Shiny » seul s’il n’y en a aucune autre (ex. une Ultra Rare ex de Destinées de Paldea numéro 92 à 223 porte « FA », pas « Shiny »). L’ancien mot « ur » n’existe plus : une rareté propre « Ultra Rare » donne « FA » ou rien. Rien n’est ajouté pour Secret / Secrète ni Alternate / Alternative (séries Épée et Bouclier notamment) : elles sont listées dans le bilan de rareté.

60. Bug du % cote (corrigé)

L’audit a trouvé précisément pourquoi certains pourcentages étaient faux.

Aujourd’hui une formule additionne parfois :

prix vendeur + coût bulk

avant de comparer à la cote.

Exemple actuel :

prix demandé : 87 €
bulk : 10,50 €
cote : 160,50 €

le programme calcule :

97,50 / 160,50 = 60,7 %

alors que le vrai pourcentage demandé est :

87 / 160,50 = 54,2 %

C’est un des bugs prévus pour Estimations V2.
Mise à jour (relue dans le code le 13/10/2026) : ce bug n’existe plus dans le code. Le % cote vient d’un seul calcul, price_to_cote_pct(prix demandé, cote totale) dans services/estimations_service.py (estimation_totals → real_pct), repris tel quel par ui/pages/estimations.py (cartes, détail, analyse, score). Le prix demandé n’est plus additionné au coût du bulk : la valeur de revente du bulk entre dans la cote totale, pas dans le prix. L’exemple ci-dessus recalculé sur une estimation de test en mémoire (prix demandé 87 €, une carte à 150 €, bulk de 10,50 € de valeur de revente) donne 160,50 € de cote et 54,2 %. Le texte qui précède décrit l’état au moment de l’audit.

Prévisions : objectif long terme (1 500 € de bénéfice moyen par mois, date limite par défaut 31/12/2028, modifiable) avec moyenne glissante sur 12 mois (ou les mois disponibles), trajectoire requise, projection « si la tendance continue » (arrêtée à 0 €), statut (sur la bonne voie / à accélérer / en retard) ; paliers 500, 1 000, 1 500, 2 000, 3 000 € ; fin d’année estimée ; objectifs annuels (CA, bénéfice, cartes) ; bénéfice cumulé ; série de mois au-dessus de l’objectif.
Un palier n’est « atteint » que si la moyenne porte sur au moins 6 mois complets.
Les objectifs sont stockés dans monthly_goals.json : un bloc par mois (clé « AAAA-MM » avec ca_target, qty_target, benef_target, auto_generated et parfois based_on), annual_goals (par année : ca_target, benef_target, qty_target) et long_term_goal (monthly_benef_target, deadline facultative). Dans la copie lue le 13/10/2026, long_term_goal n’existait pas encore dans le fichier : les valeurs par défaut s’appliquaient (1 500 € par mois, 31/12/2028).
Rotation du stock = CA de la période ÷ valeur moyenne du stock (moyenne pondérée dans le temps, courbe de stock corrigée), annualisée ; calculée depuis le début de l’historique de stock (07/06/2026).
Détails de la rotation (compute_stock_rotation) : le CA est celui des ventes datées dans la période (les ventes initiales, datées de mars, tombent avant le début de l’historique de stock) ; annualisation = rotation de la période × 365 ÷ nombre de jours (DAYS_PER_YEAR) ; en dessous de 30 jours de période (ROTATION_MIN_DAYS) la valeur est marquée « indicatif » ; la jauge va de 0 à 4× (ROTATION_SCALE_MAX) ; avec moins de 2 points d’historique de stock : « Pas assez de données ».
Délai de remboursement = jours entre la création d’un lot et la vente où ses ventes cumulées couvrent son prix d’achat. Exclus : lots saisis en bloc les 16-18 mars 2026, ventes initiales, lot Divers, lots système, lots collection.
Détails du délai (compute_lot_payback) : coût = prix d’achat effectif du lot (effective_purchase_price de logic.py) ; seules les ventes de cartes entrent dans le cumul (ni ventes initiales, ni hors stock) ; délai = 0 si la vente qui rembourse est datée avant la création du lot ; moyenne simple et médiane sur les lots remboursés seulement ; moins de 3 lots remboursés (PAYBACK_MIN_LOTS) : « Pas assez de données ». Sont aussi exclus les lots sans date de création ou sans prix d’achat (le critère est _is_payback_eligible_lot : ni système, ni is_mixte, ni is_divers). Sous les chiffres, les lots non remboursés les plus anciens sont listés (PAYBACK_PENDING_COUNT = 3), seulement si leur reste à rembourser atteint SLOW_LOT_MIN_VALUE = 20 €.
Les mois de janvier, février et mars 2026 sont estimés : l’historique saisi en mars (16-17 mars) est réparti à parts égales sur les trois mois (constantes HISTORY_IMPORT_*), marqués d’un « * ».
Les chiffres de Statistiques incluent les ventes initiales (voir section 92).
Repères code, pièges et tests de Statistiques : sections 95 à 97.

72. Mois record

Le Mois record a une règle particulière.

Il est attribué en priorité au mois qui possède le plus gros chiffre d’affaires réel de son année.

Il ne peut donc pas être distribué arbitrairement à plusieurs mois d’une même année.

En cas d’égalité, le premier mois chronologique garde le titre.

Le mois courant ne devient record que lorsqu’il dépasse réellement le record précédent.

Reset annuel automatique (ajouté le 13/10/2026) :
Au premier chargement de la page Compteurs ou de Statistiques dans une nouvelle année civile, ensure_yearly_reset (services/counters_archive_service.py) archive l’année écoulée puis remet les compteurs à zéro, en une seule écriture de counters.json (safe_write_json_synced). Déclencheur : le marqueur _archive.last_reset_year, pas le champ year (qui est le sélecteur d’affichage). Au premier passage il est posé à l’année en cours sans rien archiver (il n’y avait pas de marqueur dans counters.json avant). Ensuite le reset ne fait rien tant que le marqueur vaut l’année en cours. Si l’appli n’est pas ouverte pendant plusieurs années, chaque année manquée est archivée dans la même écriture ; une archive déjà présente n’est jamais écrasée.

Le start_datetime est indispensable : tant qu’il contient un « T », il prime sur start_date dans le calcul (counters.py), donc l’ancien horodatage continuerait de compter les ventes de l’année passée.
Où est stockée l’archive : dans counters.json, sous la clé _archive : last_reset_year et years. years["2026"] contient reset_on (« 2027-01-01 », date théorique du reset, sans heure) et channels (main_brocante, dexify, pokedeal, choppetacarte) avec label, ca, ca_ventes, nb, init_ca et start_date de l’année passée. La clé voyage donc avec counters.json (synchro cloud, sauvegarde dans backups\). counters.py accède aux clés par leur nom et aucun autre code ne lit ce fichier : _archive n’est jamais prise pour un canal.
Calcul de l’archive : par fenêtre de dates du 01/01 au 31/12 de l’année écoulée, avec les mêmes règles de comptage que les cartes (ventes initiales et bénéfices d’échange ignorés ; alias de canaux normalisés). Main propre & Brocante : les ventes de l’année civile, sans CA de départ (init_ca est archivé mais non compté, comme à l’affichage). collect_channel_counter_totals a pour cela un paramètre optionnel end_date (par défaut sans limite).
Limite : l’archive est un instantané pris au premier chargement de la nouvelle année. Une vente datée de l’année passée mais saisie ou annulée ensuite ne la modifie pas (les chiffres annuels de Statistiques, eux, sont toujours recalculés depuis les ventes).
Où la consulter : Statistiques > Performance > Années précédentes (section 69). La page Compteurs affiche un message quand une année vient d’être archivée.
Le sélecteur d’année de Main propre & Brocante est inchangé. Relu dans le code : sur les canaux Vinted qui ont un start_datetime avec « T » (Dexify et Pokédeal dans la copie du 13/10/2026), le sélecteur « Année affichée » change start_date mais le calcul continue d’utiliser start_datetime ; non modifié, non testé dans l’interface.

89. Principes économiques fondamentaux

PokéStock repose maintenant sur quelques règles très importantes.

Vente

CA = montant réellement encaissé.

Bénéfice

vente − coût historique réel.

Échange

n’est jamais une vente.

Argent reçu dans un échange

n’est jamais du CA.

Rachat

n’est jamais une vente.

Prix estimé

n’est jamais automatiquement un coût historique.

Coût inconnu

reste inconnu.

Lot

conserve l’origine économique des cartes.

Suppression

doit restaurer proprement les conséquences économiques.

C’est ce qui permet d’avoir des statistiques fiables.

92. Définitions métier à ne pas confondre (octobre 2026)

CA et Bénéfice de la barre latérale : calculés par gst() dans logic.py. Le CA additionne toutes les ventes (cartes, ventes initiales et ventes hors stock). Le « Bénéfice » est une trésorerie nette : CA moins le prix d’achat de tous les lots, stock invendu inclus. Le calcul utilise le champ prix_achat (pas prix_achat_reel : seul « Lot master set 151 » diffère, 576,32 € contre 1 600 €) et le CA exclut les bénéfices d’échange (is_exchange_benefit). Ordres de grandeur au 13/10/2026 : CA 8 966,47 € dans Statistiques et 8 966,48 € dans gst() (arrondi), bénéfice gst() 2 227,81 €, bénéfice réalisé de Statistiques 4 977,59 €.
Affichage de la barre latérale (depuis le 14/10/2026) : En stock et Valeur stock restent des totaux, jamais remis à zéro. Vendues, CA et « Bénéfice réalisé » affichent d’abord le chiffre de l’ANNÉE CIVILE en cours (année en violet clair à côté du libellé, ex. « CA · 2026 ») : il repart à zéro en janvier, sans reset ni archive, car il est recalculé depuis les ventes par fenêtre de dates du 01/01 au 31/12 (services/sidebar_stats_service.py). Dessous, en petit : « Total : X » depuis le début (Vendues 688, CA 8 966,48 € au 13/10/2026, bénéfice réalisé 4 977,59 €). Le bénéfice principal est le bénéfice réalisé (même définition que Statistiques, ventes initiales incluses, via _collect_statistics_data) ; la « Trésorerie nette » (ancien « Bénéfice » de la barre latérale, 2 227,81 € au 13/10/2026) est en petit dessous : CA de l’année moins le prix d’achat (prix_achat) des lots CRÉÉS dans l’année (date lue comme dans Statistiques : created, created_at, date_achat, date), avec « · total X » ajouté seulement quand il diffère du chiffre de l’année. Les lots saisis en bloc les 16-18 mars 2026 comptent donc dans 2026 ; un lot sans date lisible n’entre dans aucune année (il reste dans le total). Une année sans vente affiche 0 ; si le bénéfice réalisé ne peut pas être calculé il s’affiche « — ». Cartes : fond sombre arrondi, compactes (ui/sidebar.py : render_sidebar_period_stat et SIDEBAR_PERIOD_CSS) ; le bloc est dans app.py (zone ps_sidebar_stats_block).
Bénéfice réalisé de Statistiques : chaque vente moins sa part du coût d’achat du lot (le stock invendu ne compte pas). Les deux chiffres sont volontairement différents ; une mention l’explique dans la page Statistiques.
Ventes initiales : lignes de ventes avec card_name « Vente initiale » et is_lot_sale. Ce sont des montants de cartes déjà vendues avant l’enregistrement du lot (9 lignes, 2 085,60 €, saisies le 16-17 mars 2026), PAS des ventes de lots entiers. Elles comptent dans le CA, le bénéfice, le ROI et le remboursement des lots, mais pas dans les transactions, le panier moyen, le nombre de cartes vendues ni la « plus grosse transaction ». Vérifié sur la copie de données du 13/10/2026 : 9 lignes (une par lot, 9 lots différents), 2 085,60 €, datées des 16 et 17 mars 2026. Elles sont stockées dans lot["ventes"] avec les 4 ventes hors stock (25,40 €) et 10 lignes de bénéfice d’échange (is_exchange_benefit, exclues du CA). Elles sont ignorées par les compteurs, l’Historique et Wrapped.
Historique saisi en bloc : l’application n’existait pas avant mars 2026 ; tout le passé a été saisi les 16-18 mars (10 lots créés ces jours-là : 8 le 16, 1 le 17, 1 le 18 ; constante HISTORY_BULK_LOT_DAYS). Les dates ne sont donc pas fiables avant cette date. L’historique de la valeur du stock ne commence que le 07/06/2026.
Cartes stockées : une carte mise de côté reste dans son lot d’origine (stored_quantity, storage_entries) et une copie est ajoutée au lot « Stockage ». Elle ne doit compter qu’une fois dans le stock : reste = max(quantité − vendues − échangées − stockées, 0), comme card_available_qty. La correction est appliquée dans gst() (logic.py) et dans _stock_value_from_state (services/stock_history_service.py), au 13/10/2026 (constante STOCK_DOUBLE_COUNT_FIX_AT). Résultat ce jour-là : 919 cartes en stock pour 6 656,39 €. La courbe de valeur du stock passée est corrigée à l’affichage seulement (corrected_stock_history_points, utilisé par home.py et Statistiques ; stock_value_history.json n’est pas modifié).
Lots collection (is_mixte) : ils ne sont pas à rembourser par les ventes ; Statistiques les affiche à part (« Lots collection conservés »).
Cartes vendues : définition unique = cartes physiques sorties du stock par vente (688 au 13/10/2026). Les échanges donnés, les ventes hors stock et les ventes initiales sont exclus. Dans le code : gst() soustrait _exchange_given_quantity (sold_entries is_exchange) ; Statistiques utilise _physical_sale_quantity. Historique et Wrapped affichent encore 697 (non corrigé, décision de laisser tel quel, commentaire dans ui/pages/history.py) : ils comptent des lignes de vente, donc 688 + 4 ventes hors stock + 5 lignes d’allocation d’une carte reçue en échange (la quantité entière est reprise sur chaque ligne), selon l’analyse du 13/10/2026.
Lots à rembourser (Statistiques > Performance) : les lots système (Trade, Stockage, Collection) n’y comptent pas (_is_system_lot) et les lots collection (is_mixte) sont affichés à part. Le lot « 🗂️ Divers » (is_divers) COMPTE dans cet indicateur (coût 127,26 €, déjà remboursé au 13/10/2026) : il n’est exclu que du délai de remboursement (_is_payback_eligible_lot).

96. Pièges rencontrés (octobre 2026)

Lots particuliers, ne pas les confondre : is_mixte = Lot Collection partielle (coût = prix_achat_reel, affiché à part dans « Lots collection conservés ») ; is_divers = « 🗂️ Divers » (aussi is_brocante, compte dans Lots à rembourser, exclu du délai de remboursement) ; lots système = is_trade, is_storage, is_collection_lot, ou nom contenant « trade », « stockage » ou « collection » (_is_system_lot). Conséquence : un lot normal dont le nom contient « collection » serait traité comme un lot système.
Trois façons de calculer le coût d’un lot existent : gst() utilise prix_achat ; effective_purchase_price (logic.py) utilise prix_achat_reel seulement pour is_mixte ; _lot_cost_map (Statistiques) utilise prix_achat_reel s’il existe. Sur les données du 13/10/2026 seul « Lot master set 151 » a un prix_achat_reel, donc aucun écart en pratique.
Ventes hors stock : dans le CA et le bénéfice, jamais dans les cartes vendues, les transactions ni les lots (_lot_rows_for les ignore).
Ventes initiales : dans le CA, le bénéfice, le ROI et le remboursement des lots ; ni transactions, ni panier, ni cartes. Ignorées par Historique, Wrapped et les compteurs.
Échanges : une carte donnée en échange (sold_entries is_exchange, 0 €) sort du stock mais n’est pas vendue ; ses lignes d’allocation et les is_exchange_benefit sont à ignorer selon l’endroit. Les doublons d’allocation expliquent l’écart 697 / 688 dans Historique et Wrapped.
Carte stockée : elle existe deux fois dans les données (lot d’origine avec stored_quantity, copie dans « Stockage »). Toute formule de stock doit soustraire stored_quantity.
Anciennes sauvegardes de data.json manquantes : les points « backup » anciens de la courbe du stock ne peuvent pas tous être recalculés ; la correction se fait alors par estimation (valeur cumulée stockée retranchée).
Arrondis : le CA vaut 8 966,47 € dans Statistiques et 8 966,48 € dans gst() ; ce n’est pas une erreur de logique.
Tests : ne jamais viser les vraies données. gst() est mis en cache, un test doit contourner le cache ou travailler sur des fixtures temporaires, et comparer le md5 des JSON avant et après.
Extensions : un champ set vide n’est pas « N/A » ; ne jamais remplacer une extension déjà renseignée sans confirmation explicite. Une carte du Drop a une copie du set : corriger le stock sans corriger la copie du Drop (ou l’inverse) crée un écart ; passer par apply_corrections(). L’empreinte d’identité (card_identity_fingerprint) inclut le set : après correction, relancer « Mettre à jour l’analyse ».

98. Extensions manquantes et Santé des données (octobre 2026)

Cause : voir section 84 (clés compactes du cache). Une carte ajoutée au stock avec un set vide n’a ni extension dans l’annonce ni empreinte d’identité fiable. Au 15/10/2026 : 114 cartes du stock sans extension (dont 54 dans le Drop), 0 dans les archives.

Garde-fou central : dans data.sd(), complete_new_cards_extension() complète le set des seules nouvelles cartes (card_uid absent du data.json sur disque) à partir de leur id dans le catalogue local (cards_cache.json et sets_reference.json). Il ne remplace jamais une extension existante et n’écrit rien quand l’id est inconnu.

Écran : Santé des données (ui/pages/data_health.py) affiche en permanence les compteurs « Cartes sans extension » (stock et Drop), puis trois sections : Anomalies (contenu historique de la page), Extensions manquantes (ui/pages/extension_queue.py) et Annonces en ligne à mettre à jour sur Vinted.
- Extensions manquantes : vues Certaines (application en bloc après aperçu et confirmation), Probables (cases à cocher + « Appliquer les cases cochées »), À choisir (sélecteur avec candidats préremplis et saisie libre). Filtres par lot et par statut Drop.
- Les cartes japonaises à drapeau seul comptent comme manquantes. Le set « Nuit Noire » (me05, Méga-Évolution) est ajouté au catalogue par EXTRA_SET_NAMES.
- Annonces en ligne à mettre à jour : liste en lecture seule des annonces en ligne dont le titre a été généré sans extension, avec titre et description corrigés (mêmes générateurs), boutons Copier et « Marquer comme mis à jour » (mémorisé hors des JSON métier). Les statuts ne changent jamais. Depuis le 15/10/2026 la même section affiche en tête les textes régénérés à reporter sur Vinted (voir section 43).

Écriture : apply_corrections() remplit uniquement les set vides (stock et copies du Drop), sauvegarde data.json et vinted_drops.json dans backups\ avant d’écrire, journalise chaque carte dans logs\extension_corrections_journal.jsonl, et undo_batch() annule un lot si la valeur courante est toujours celle écrite. Jamais de changement de statut, de date, de photo ni de groupe.

Trace de diagnostic (désactivée par défaut) : créer le fichier logs\trace_extension.on (ou la variable POKESTOCK_TRACE_EXTENSION) ; les ajouts de cartes écrivent alors dans logs\extension_trace.log, jamais dans les JSON métier.
